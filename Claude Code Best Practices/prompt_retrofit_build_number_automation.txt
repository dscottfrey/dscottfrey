## Goal

Retrofit this existing Xcode project with an automated build-number-and-build-identifier system.

Every build will regenerate a gitignored `BuildInfo.swift` containing a build timestamp, the short git SHA of HEAD, and a flag indicating whether the working tree was dirty. Release builds will additionally bump `CFBundleVersion` in `Info.plist` so the project is App Store / TestFlight ready (those channels require monotonically increasing build numbers per marketing version). Debug builds will not touch `Info.plist`, so day-to-day rebuilding does not pollute `git status`.

An About screen will display: the marketing version (`CFBundleShortVersionString`), the build timestamp, and the short SHA with a `+` suffix when the tree is dirty. Example: `1.2.0 (2604051847 · a3f9c1e+)`.

The reason this matters is troubleshooting. When a bug report or screenshot arrives and you cannot tell which build it came from, the first ten minutes of debugging are wasted figuring that out. Manual build-number incrementing fails closed — humans forget exactly when the information matters most. Automation removes the failure mode.

## Phase 2 — File-level changes Claude Code performs

Once confirmed, perform these steps in order. After each, briefly report what you did before moving to the next.

### 2.1 — Create the build-info generator script

Create a tracked-in-git script file at the project root:

```
Scripts/generate_build_info.sh
```

Make it executable (`chmod +x`). Contents:

```bash
#!/bin/bash
# Generate BuildInfo.swift with a build timestamp, short git SHA, and dirty marker.
# On Release builds, also bump CFBundleVersion in Info.plist for App Store / TestFlight.
#
# Called from a Run Script build phase. See README in this script's folder, or the
# project's build CLAUDE.md, for the wiring details.

set -e

# --- Compute build identifier values ---

TIMESTAMP=$(date +%Y%m%d%H%M)

# Build phases run with a minimal PATH; locate git via xcrun or fall back.
GIT=$(xcrun -find git 2>/dev/null || which git || echo "/usr/bin/git")

if [ -x "$GIT" ] && "$GIT" -C "$SRCROOT" rev-parse --git-dir > /dev/null 2>&1; then
    GIT_SHA=$("$GIT" -C "$SRCROOT" rev-parse --short HEAD 2>/dev/null || echo "nohead")
    if "$GIT" -C "$SRCROOT" diff --quiet 2>/dev/null && \
       "$GIT" -C "$SRCROOT" diff --cached --quiet 2>/dev/null; then
        IS_DIRTY="false"
    else
        IS_DIRTY="true"
    fi
else
    GIT_SHA="nogit"
    IS_DIRTY="false"
fi

# --- Write BuildInfo.swift ---

# BUILD_INFO_PATH is passed in as the first argument so this script works for
# any target / any source folder layout.
BUILD_INFO_PATH="$1"

if [ -z "$BUILD_INFO_PATH" ]; then
    echo "error: generate_build_info.sh requires the BuildInfo.swift output path as its first argument"
    exit 1
fi

mkdir -p "$(dirname "$BUILD_INFO_PATH")"

cat > "$BUILD_INFO_PATH" <<EOF
// BuildInfo.swift
// AUTO-GENERATED at build time. Do not edit by hand. Do not commit (gitignored).
// See the project's build CLAUDE.md for the rationale.

enum BuildInfo {
    static let timestamp: String = "$TIMESTAMP"
    static let gitSHA: String = "$GIT_SHA"
    static let isDirty: Bool = $IS_DIRTY
    static let configuration: String = "$CONFIGURATION"

    /// Display string suitable for an About screen, e.g. "2604051847 · a3f9c1e+"
    static var displayString: String {
        let dirtyMarker = isDirty ? "+" : ""
        return "\(timestamp) · \(gitSHA)\(dirtyMarker)"
    }
}
EOF

# --- On Release, bump CFBundleVersion for App Store / TestFlight ---

if [ "$CONFIGURATION" = "Release" ]; then
    if [ -n "$INFOPLIST_FILE" ] && [ -f "${SRCROOT}/${INFOPLIST_FILE}" ]; then
        # Hand-maintained Info.plist file.
        /usr/libexec/PlistBuddy -c "Set :CFBundleVersion $TIMESTAMP" "${SRCROOT}/${INFOPLIST_FILE}"
        echo "Release build: CFBundleVersion set to $TIMESTAMP in ${INFOPLIST_FILE}"
    else
        # Modern Xcode (GENERATE_INFOPLIST_FILE = YES) — Info.plist is built from
        # build settings. The corresponding setting is CURRENT_PROJECT_VERSION,
        # typically supplied via an .xcconfig file. Update it there if present.
        # If neither path applies, surface a warning so the human can wire it up.
        echo "warning: No hand-maintained Info.plist found at \$SRCROOT/\$INFOPLIST_FILE — for generated-Info.plist projects, set CURRENT_PROJECT_VERSION via xcconfig and update it from a scheme pre-action. See project build CLAUDE.md."
    fi
fi

echo "BuildInfo: $TIMESTAMP $GIT_SHA dirty=$IS_DIRTY config=$CONFIGURATION"
```

```swift
enum BuildInfo {
    static let timestamp: String = "000000000000"
    static let gitSHA: String = "uninit"

        let dirtyMarker = isDirty ? "+" : ""
        return "\(timestamp) · \(gitSHA)\(dirtyMarker)"
    }
}
```

### 2.4 — Add or update the About view

For each app target:

- **iOS (SwiftUI):** if no About view exists, create `<target_source_folder>/Views/AboutView.swift`. If one exists, add the build-identifier line to it (do not redesign existing UI without explicit permission).

```swift
import SwiftUI

struct AboutView: View {
    private var appName: String {
        Bundle.main.infoDictionary?["CFBundleName"] as? String ?? "App"
    }

    private var marketingVersion: String {
        Bundle.main.infoDictionary?["CFBundleShortVersionString"] as? String ?? "—"
    }

    var body: some View {
        VStack(spacing: 12) {
            Text(appName)
                .font(.title2)
            Text("Version \(marketingVersion)")
                .font(.subheadline)
            // Full build identifier — uniquely identifies which build this is.
            // Mention this string when reporting issues or comparing screenshots.
            Text("Build \(BuildInfo.displayString)")
                .font(.caption)
                .foregroundStyle(.secondary)
                .textSelection(.enabled)
        }
        .padding()
    }
}
```

If the project has no existing About entry point in its UI, surface that fact and propose where to wire one in (e.g., a Settings row) — do not add UI navigation without confirmation.

- **macOS:** if the project relies on the standard About panel, add a small helper that injects the build identifier into the Credits area:

```swift
import AppKit

@MainActor
enum AboutPanel {
    static func show() {
        let credits = NSAttributedString(
            string: "Build \(BuildInfo.displayString)",
            attributes: [
                .font: NSFont.systemFont(ofSize: NSFont.smallSystemFontSize),
                .foregroundColor: NSColor.secondaryLabelColor
            ]
        )
        NSApp.orderFrontStandardAboutPanel(options: [
            .credits: credits
        ])
    }
}
```

Then surface to the user that they need to wire the existing "About <App>" menu item to call `AboutPanel.show()` (this is a `MainMenu.xib` / storyboard / SwiftUI App command edit depending on the project structure). If the project is a SwiftUI macOS app using `App` and `Scene`, propose using `.commands { CommandGroup(replacing: .appInfo) { Button("About \(appName)") { AboutPanel.show() } } }` and ask before adding it.

If the project has a custom About window, add the same `Build \(BuildInfo.displayString)` line to it.

## Phase 3 — Steps the human must do in Xcode

Claude Code cannot click around in the Xcode UI. After you finish Phase 2, give the user a single concise checklist of the manual steps required:

1. **Add the placeholder `BuildInfo.swift` files to their respective targets.** Drag each new `Generated/BuildInfo.swift` into the project navigator under the right target. Confirm "Add to target" is checked for the matching app target. Do not check "Copy items if needed" if the file is already inside `$SRCROOT`.

2. **Add a Run Script build phase to each app target.** Target → Build Phases → `+` → New Run Script Phase. Name it `Generate BuildInfo`. **Drag it above "Compile Sources"** so the file exists before the compiler reads it. Uncheck "Based on dependency analysis" so it runs every build.

3. **In the Run Script phase, paste:**

   ```bash
   "${SRCROOT}/Scripts/generate_build_info.sh" "${SRCROOT}/<target_source_folder>/Generated/BuildInfo.swift"
   ```

   Replace `<target_source_folder>` with the actual folder name for each target (Claude Code will provide the exact line per target in its summary).

4. **Build once (Debug).** Confirm `BuildInfo.swift` is updated with a real timestamp and SHA, the app compiles, and the About screen shows the new build identifier.

5. **Archive once (Release).** Confirm `Info.plist` shows a new `CFBundleVersion` matching the timestamp, and that `git status` reflects only that change (no `BuildInfo.swift`).

6. **Commit the new files.** `Scripts/generate_build_info.sh`, the placeholder `BuildInfo.swift` (only the placeholder version, before the script overwrites it — or just commit after running `git rm --cached` per the gitignore), the `.gitignore` update, and any About view changes.

## Things this retrofit does NOT do

- Does not change the existing marketing version (`CFBundleShortVersionString`). That stays under human control.
- Does not redesign any existing About UI. It adds one line; it does not restructure.
- Does not modify any CI configuration. If the project is built by Xcode Cloud, GitHub Actions, or Fastlane, surface that and ask how to integrate — the right answer depends on the CI platform.
- Does not remove or modify any pre-existing version-management build phase. If one exists, surface it during the survey and ask how to handle the conflict.
- Does not edit the `.pbxproj` to add the Run Script phase. That step is intentionally left for the human in Xcode UI to avoid risk to project integrity.
